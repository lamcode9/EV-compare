Internationalization (i18n) Groundwork

battery.mom · foundation for Bahasa Melayu, Bahasa Indonesia, Thai, and Vietnamese

What this is. A dictionary-based translation foundation that lets UI strings be localized incrementally with graceful English fallback. It is deliberately groundwork: it does not add locale-prefixed routing or rewire components — those are the next adoption steps, scoped below. Roadmap item: pipeline/PLAN.md §4.1.

What was built

FileRole
lib/i18n/config.tsLocale list (en, ms, id, th, vi), default locale, isLocale() guard, and per-locale display metadata (endonym, flag, direction).
lib/i18n/dictionaries/en.tsBase dictionary — the source of truth. Dictionary type is inferred from it.
lib/i18n/dictionaries/{ms,id,th,vi}.tsPartial locale overrides. Only translated keys are present; the rest fall back to English.
lib/i18n/getDictionary.tsServer-side loader. Lazily imports the requested locale and deep-merges it over English.
lib/i18n/types.tsDeepPartial / LocaleDictionary types so overrides stay type-checked against the base.
lib/i18n/index.tsPublic barrel export.
lib/i18n/__tests__/getDictionary.test.ts6 tests: metadata coverage, key fallback, and full-key resolution per locale.

How to use it (server components)

import { getDictionary } from '@/lib/i18n'

// locale resolved from route/header — see adoption step 1
const t = await getDictionary(locale)

return <h1>{t.ev.searchAndCompare}</h1>

For client components, resolve the dictionary in the nearest server component and pass it down as a prop. Any key not yet translated for the chosen locale automatically renders the English string.

Translation status

Core chrome (navigation, common buttons, country selector, EV search heading, footer) is seeded with high-confidence translations. Everything else falls back to English until filled in. All seeded strings still need a native-speaker review pass before any locale is marketed as complete.

Adoption plan (next steps)

  1. Locale routing & detection todo — add a [lang] segment (or middleware-based locale negotiation from the Accept-Language header) so a locale can be resolved per request and passed to getDictionary.
  2. Language switcher todo — a small picker driven by localeMeta; persists choice (cookie) and updates the URL.
  3. Wire chrome to the dictionary todo — replace hardcoded strings in Header, Footer, the EV search page, and shared error/loading UI with t.* lookups.
  4. Expand the dictionary todo — migrate remaining UI strings into en.ts, then translate per locale. Long-form editorial articles are a separate content workstream.
  5. Locale-aware metadata & hreflang todo — emit per-locale <link rel="alternate" hreflang> tags and translate route metadata for SEO.
  6. Number / currency / date formatting todo — the app already uses Intl via toLocaleString; thread the active locale through those calls.

Design decisions

  • Dictionary + fallback over a heavy i18n library. No new runtime dependency; partial translations ship safely because missing keys degrade to English.
  • Type-inferred dictionary. Adding a key to en.ts makes it available everywhere and keeps locale overrides validated against the canonical shape.
  • Lazy locale imports. Only the requested language's strings enter a request's bundle.
